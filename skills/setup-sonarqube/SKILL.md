# Optional SonarQube setup

Provision and verify local SonarQube for the current project. An explicit `/setup-sonarqube` request or acceptance of the setup offer authorizes this local workflow. Discovery alone grants no provisioning permission. Preserve existing configuration and data; never publish, change remote services, reset credentials, delete volumes, or weaken a shared gate without the corresponding user authorization. Follow the [shared goal policy](../../assets/global-stack-policy.md).

Before automatic development-goal scanner/readback/token operations, resolve project-root `kiss-chris-stack.config.json` through [evaluate](../evaluate/SKILL.md). `evaluation.sonarqube.enabled` defaults to `true`; an explicit `false` disables this evaluation gate and skips those operations without removing services, credentials or scanner configuration. Report disabled/skipped rather than passed. Invalid configuration blocks evaluation, and agents must never edit switches to evade failures. An explicit setup request still governs provisioning; do not silently rewrite an existing switch, and explain when gate verification is disabled.

## Discover and prepare

1. Read project instructions, documentation, build/test configuration and existing Sonar configuration. Identify actual components and their source/test roots; Java backend and React/TypeScript frontend are examples, not mandatory projects. Reuse an existing working SonarQube instance and projects when configured; an unreachable configured service is a failure, not absence. An empty/documentation-only project needs no invented application or fake coverage.
2. Run `python "<this-skill>/scripts/check-container-runtime.py"`. It checks reachable Linux Docker/Podman engines without starting anything; Docker Desktop and Rancher Desktop normally expose `docker`, Podman exposes `podman`. Its `available` flag is an initial prerequisite only. If unavailable, explain the actual missing/stopped engine and that the skill can run later after Docker or another compatible runtime is installed/started. Do not block normal stack setup.
3. Inspect the actual engine endpoint/context and environment (including `DOCKER_HOST`/Podman connections): a reachable engine may be remote. Local consent covers a local Desktop/VM engine only; require separate explicit authorization before modifying a remote/external engine. Before provisioning, check architecture, free memory/disk, available loopback port, image compatibility and current [SonarQube Docker requirements](https://docs.sonarsource.com/sonarqube-community-build/server-installation/from-docker-image/installation-overview). Use official supported images and record an explicit version/digest, never a moving `latest` tag. Check Linux host/VM kernel requirements including Elasticsearch limits; do not change host sysctl, desktop settings or privileged permissions automatically. If required, explain the concrete prerequisite and wait for its resolution.
4. Before writing any secret, ensure the project-root `.env` is untracked (`git ls-files --error-unmatch -- .env` must not succeed), add `/.env` to `.gitignore`, and prove it is ignored with `git check-ignore -- .env`. A tracked `.env` needs user resolution; adding an ignore rule does not untrack it. Preserve unrelated `.env` bytes/keys, comments and existing valid Sonar credentials. Reject duplicate/conflicting Sonar keys rather than guessing. For non-Git projects protect `.env` with owner-only permissions and establish the future ignore rule. Never source/eval arbitrary `.env` content. Use proper dotenv quoting and a same-directory atomic replacement with restricted permissions/ACL, including temporary files. No secrets in terminal output, logs, command arguments, docs, traces, Compose files or committed examples.

## Container, login and token

1. Inspect existing named resources before creation. Use project-specific names, named persistent volumes, a private network when a database is needed, and bind HTTP to `127.0.0.1` only. Never replace an unknown container or reuse someone else's volume. Use a supported PostgreSQL database for durable use; the embedded database is for evaluation only and must be labeled accordingly. Reuse the project's Compose conventions when present; otherwise the following illustrates a local evaluation container after resolving the image digest and project-specific names:

   ```sh
   docker run -d --name <project>-sonarqube --publish 127.0.0.1:9000:9000 --mount source=<project>-sonar-data,target=/opt/sonarqube/data --mount source=<project>-sonar-extensions,target=/opt/sonarqube/extensions --mount source=<project>-sonar-logs,target=/opt/sonarqube/logs sonarqube@sha256:<verified-digest>
   ```

   Substitute `podman` for that engine; use official database/JDBC configuration for durable installation. Store connection secrets in the protected project `.env`, never inline in the recorded command. Configure restart behavior using the chosen runtime's supported mechanism. Record nonsecret image/container/volume names and startup/stop commands in project docs. Reruns start/reuse matching resources and preserve their data; never run `down -v` or prune.
2. Poll `GET /api/system/status` with a bounded startup timeout (for example 5 minutes, each HTTP request at most 10 seconds) until `UP`. Surface failure/timeout without printing secret-bearing logs. Read `/api/server/version`, the running server's `/web_api` and current official documentation before mutations; endpoint parameters and metrics vary between versions/editions. [Web API guidance](https://docs.sonarsource.com/sonarqube-server/extension-guide/web-api) requires form-encoded POST bodies; use authenticated HTTP requests in-process rather than secret-bearing shell arguments.
3. On a newly created instance only, authenticate using the documented factory login and generate a cryptographically random password. Atomically save the candidate as `SONAR_PENDING_PASSWORD` in the protected `.env` **before** changing server credentials; stop before mutation if secure persistence fails. Immediately replace the factory password through `POST /api/users/change_password` (login, previousPassword, password), then verify authentication via `GET /api/authentication/validate`. Finalize `SONAR_PASSWORD` and remove the pending key only after verification and successful atomic persistence; retain the recoverable candidate if finalization fails. On a rerun resolve pending state by authentication, never by blindly changing credentials again. On an existing instance reuse its valid login and never reset its password implicitly. Save `SONAR_HOST_URL`, `SONAR_LOGIN`, `SONAR_PASSWORD` in `.env`; do not display their values. Give the user the local URL and path to credentials.
4. Use the validated login for project/gate administration; keep administrative credentials separate from scanner tokens. After creating the projects below, create a named token with `POST /api/user_tokens/generate`, using only the permissions and expiration needed for those existing projects; prefer project analysis tokens for scanners. Persist the returned token and its managed name/owner/type/project binding/expiry together once as `SONAR_TOKEN` plus slot metadata (or distinct component token keys), verify it by authenticated request and record expiration without the value. Apply the same initial identity mapping when creating the reader token. If an existing token is valid, reuse it; enroll legacy metadata only through the unequivocal mapping described below. Never blindly rotate/revoke tokens on reruns. If token creation succeeds but persistence fails, report the incomplete state without exposing the token and safely revoke only the token created by this invocation if authorized. Read [token guidance](https://docs.sonarsource.com/sonarqube-server/user-guide/managing-tokens).

Validate generated passwords against the installed server's policy before submission (for example uppercase, lowercase, digits and a special character). A random URL-safe string alone may fail that policy; retain the protected candidate and correct it without exposing values.

When creating managed scanner or reader tokens, atomically store their server token name, owner login, token type, project binding where applicable, and expiration alongside their protected `.env` token slot. Use slot-specific metadata such as `SONAR_TOKEN_NAME`, `SONAR_TOKEN_OWNER`, `SONAR_TOKEN_TYPE`, `SONAR_TOKEN_PROJECT_KEY` and `SONAR_TOKEN_EXPIRES_AT`, with corresponding prefixes for fixture/reader slots. Preserve the finite lifetime policy. Enroll an existing token only when its identity maps unequivocally from known configuration/creation evidence to server metadata; matching a project/type or guessing from a token string/name alone is insufficient. Do not rotate healthy tokens to fill missing metadata.

## Reader credentials and findings

Project analysis tokens authorize **Execute Analysis** services; successful upload or `/api/authentication/validate` does not prove that findings or source can be read. Keep scanners' project analysis tokens separate from a least-privilege **user token** saved as `SONAR_READER_TOKEN` in the protected `.env`. Create a dedicated service user with per-project **Browse** and **See Source Code** permissions (and Execute Analysis only when this user also scans). Do not grant global administration, project administration or issue acceptance merely to read results. Preserve its generated login/password in `.env` with the same pre-mutation persistence rules. Restrict projects to private when authorized so anonymous visibility cannot mask missing permissions.

Use the installed API's `POST /api/users/create` for a missing local service user, `POST /api/permissions/add_user` with per-project `user` (Browse), `codeviewer` (See Source Code) and optional `scan` (Execute Analysis), then `POST /api/user_tokens/generate` with `type=USER_TOKEN` and that user's login. Reuse an existing valid user/token and preserve unrelated users and existing shared global policy.

Audit **effective** permissions, including inherited **group** grants, through `/api/users/current` with the reader token and administrative permission/group inspection. Direct grants alone do not prove least privilege. The reader must have no global permissions: no provisioning/create-project or global scan rights, and no access to unrelated projects. Inspect project permission groups and the default permission template as well: inherited `issueadmin` and `securityhotspotadmin` allow accepting issues or reviewing hotspots even when global permissions are empty. The automation reader must not inherit those administration rights. On a newly provisioned dedicated instance, remove unnecessary default-group global/project/template grants if required (default-group membership may be immutable), preserving administrators' needed scan permission and the reader's explicit project Browse/See Source Code grants. Do not change inherited group/global/project/template policies on an existing/shared instance without separate authorization; explain the concrete conflict instead. Recheck effective global permissions are empty, effective per-project permissions are limited, future template grants do not broaden access, and both real upload and findings/source readback still work.

After an actual upload, prove the reader token can read `/api/issues/search`, `/api/measures/component`, `/api/sources/lines`, `/api/ce/task` and `/api/qualitygates/project_status` for every relevant project. Discover a real file key through `/api/components/tree`; bind task and analysis IDs to that upload. Treat HTTP 401 and 403 as failures even when authentication validation or scanner upload succeeded. Use [read-analysis.py](scripts/read-analysis.py) with `SONAR_HOST_URL` and `SONAR_READER_TOKEN` in its environment and explicit `--project`, `--task-id`, `--analysis-id` and `--source-key` arguments. It checks all five read paths and exits nonzero on any forbidden request; its JSON contains findings, measures, source and gate evidence for diagnosis. The issues request returns the first 100 issues for access verification; paginate the API when investigating a larger result set.

After tightening inherited grants, also validate the separate human/administrator login can browse each configured project and read source. Global administration does not necessarily confer project Browse/See Source Code or hotspot-review permissions. Preserve or grant these explicitly to the authorized human administrator as needed, then verify project/source/dashboard access using that login; never copy administrative grants to the automation reader.

## Automatic renewal of expired managed tokens

Run this renewal preflight **before every scanner upload, reader request and quality gate check**, including normal development goals and resumed work. The user's automatic-renewal instruction authorizes renewal of confirmed expired managed tokens on the configured host using already protected owner credentials. Successful renewal is silent, without another confirmation or chat notification. Preserve existing shared/external authorization boundaries; do not reset passwords or change permissions to make renewal succeed.

1. Serialize every project token refresh through the same exclusive `.sonar-evidence/token-refresh.lock` (ensure `.sonar-evidence/` is ignored), using a bounded wait. After acquiring it, re-read the protected `.env` as data and current server metadata so another agent's completed renewal is reused rather than overwritten. Preserve ACL/owner-only permissions on lock/staging files; do not delete another live process's lock or log credentials.
2. Authenticate token management with the stored **owner** login/password (or an already authorized administrator for that owner). Query `/api/user_tokens/search?login=<owner>`; verify the managed token name, owner, type, expiration and project binding. The installed API may return project binding as `project.key`. Use server expiration metadata/time, or its documented token-expiration header where present; `/api/authentication/validate` alone provides no expiry proof. Reuse healthy tokens unchanged.
3. Renew only a known managed token confirmed **expired**. A 401 or 403 alone does not establish expiration: revoked/missing tokens, wrong credentials, wrong project, insufficient permission and unavailable servers are distinct failures. Do not automatically recreate revoked, unowned or ambiguously mapped credentials. Surface the concrete failure and keep the quality gate blocking when it cannot be resolved within existing authorization.
4. Generate one uniquely named replacement via `POST /api/user_tokens/generate`, retaining the **same owner, type and project scope**, least privilege and finite expiry policy. A scanner `PROJECT_ANALYSIS_TOKEN` remains bound to its existing project; the reader remains a `USER_TOKEN` owned by the restricted service user. Verify creation metadata and intended permissions, never replace either with a broad administrative token or grant extra rights.
5. Before persistence, verify replacement authentication and identity/type/scope/permission metadata only; do not perform a trial scanner upload. Atomically persist the token plus its management identity/expiry in `.env`, preserving comments, unrelated keys and restrictive ACL; reload the child environment from the committed file. Then execute the pending scanner/read operation **once** as both operation-specific validation and its **one bounded retry**, using the existing operation timeout. Authentication validation alone does not prove that operation: reader validation includes the required issue/measure/source/task/gate endpoints, and scanner validation is this single actual scoped analysis. Do not recursively renew or upload a second time. Revoke only the old managed token (`POST /api/user_tokens/revoke`, owner login and old name) after the replacement is persisted and that intended operation succeeds.
6. Keep the lock until the replacement state is consistent, then release it. If generation succeeds but persistence/validation fails, revoke only the newly created orphan when it is not referenced by committed configuration; never revoke a working concurrent replacement or the prior token before successful replacement. Retain a safely persisted replacement for recovery if a later server operation fails, report cleanup failures without secrets, and leave the goal blocked. Failure is visible; successful renewal remains quiet.

This runs transparently on use/resume while an agent or process is active. It does not install a daemon or scheduled service and cannot renew while nothing is running. The low-level scanner and `read-analysis.py` do not renew tokens themselves; the agent must complete this skill preflight before invoking them. Missing owner credentials, unsafe storage or an unresolved lock remains a blocking failure rather than a prompt to weaken authentication or gates.

## Projects, analysis and strict quality gate

1. Use one Sonar project per independently analyzed component, or retain an existing coherent multi-module project. Inspect `/api/projects/search` and create missing projects via `POST /api/projects/create` using deterministic repository/component keys. Record keys, component paths, language profiles, coverage files, scanner/test commands and the selected gate in a nonsecret project document/configuration. Store host, login, token(s), project keys, gate identifier, image/container references and any JDBC credentials needed for repeat analysis/login in `.env`. Do not invent Java or frontend projects when those components do not exist.
2. Reuse native builds and installed scanners; pin any necessary scanner/plugin version after checking compatibility. Java Maven/Gradle requires compiled bytecode and a fresh JaCoCo XML report (`sonar.coverage.jacoco.xmlReportPaths`); run the existing test/coverage task before its native Sonar scanner. For Maven, a typical command is `./mvnw verify org.sonarsource.scanner.maven:sonar-maven-plugin:<verified-version>:sonar -Dsonar.qualitygate.wait=true`; Gradle uses the existing `test jacocoTestReport sonar` tasks (Windows wrappers where appropriate). React/TypeScript requires the existing test runner to produce fresh LCOV and `sonar.javascript.lcov.reportPaths`; run its actual coverage script, then the installed `sonar-scanner -Dsonar.qualitygate.wait=true` from the configured component root. Apply equivalent supported scanners/reports to other detected languages. Separate source and tests and exclude generated/dependency artifacts using existing conventions. No broad coverage exclusions, fabricated reports or changed business behavior to get green. Missing reports or unexpectedly missing analyzable source are failures, even when the server does not compute coverage.
3. Create a dedicated project-owned gate (for example `<repo>-strict`) using `POST /api/qualitygates/create`, inspect it with `/api/qualitygates/show`, add conditions using `/api/qualitygates/create_condition`, and assign it to each relevant project with `/api/qualitygates/select`. Query available metrics and served API first. These defaults apply to **overall code**, including existing debt:

   | Metric | Fail condition |
   | --- | --- |
   | Vulnerabilities (`vulnerabilities`) | greater than 0 |
   | Bugs (`bugs`) | greater than 0 |
   | Code smells (`code_smells`) | greater than 0 |
   | Test coverage (`coverage`) | less than 80 percent |

   Use API operators `GT` with error threshold `0` for each issue count and `LT` with error threshold `80` for coverage, after confirming the installed API parameter names. Verify server mode (Standard Experience versus MQR), metric availability and actual saved conditions. Do not substitute A ratings, new-code-only metrics or rounded estimates for zero issue counts. If this edition cannot express the defaults, stop and explain the needed supported mode/version or ask for an explicit threshold decision. Never silently lower thresholds, edit the global default/shared gate or mark issues accepted to pass. For languages with security hotspots, require their review as well. Disable any small-change coverage bypass when applicable and verify the effective setting. [Sonar's gate model](https://docs.sonarsource.com/sonarqube-community-build/quality-standards-administration/managing-quality-gates/introduction-to-quality-gates) explains why ratings alone do not enforce zero issues.

   Once projects, gate and scanners are configured, persist the nonsecret project instruction/configuration that activates the canonical quality gate rule **before the first analysis**. A red scan or interrupted initial analysis must not leave later goals exempt. Then mint/reuse the project analysis tokens described above.
4. Run initial test/coverage and scanner uploads for every relevant project using environment variables `SONAR_HOST_URL` and `SONAR_TOKEN` from the protected `.env`; scanners do not universally load dotenv themselves. Set `sonar.qualitygate.wait=true` with a bounded timeout. [Analysis parameters](https://docs.sonarsource.com/sonarqube-server/analyzing-source-code/analysis-parameters/parameters-not-settable-in-ui) describe these supported settings. A containerized scanner needs a reachable internal service URL/network; its `localhost` is not the host. Keep the browser URL separate where needed and never expose SonarQube publicly to solve connectivity.

## Prove setup and enforce completion

Preserve each scanner's `report-task.txt` outside source control. Poll its `ceTaskId` through `/api/ce/task` until success within a bounded timeout, obtain its `analysisId`, and query `/api/qualitygates/project_status?analysisId=<that-analysis-id>`. Require `OK` for all configured projects and verify expected metrics, coverage and assigned gate. An upload exit code alone, a previous dashboard pass, an unrelated project/branch, a pending task, missing coverage or a failed/unreachable service is not completion evidence. Community editions may lack branch/PR analysis: analyze the actual working tree using a supported mode and never send unsupported branch flags or use another branch's pass.

Record the analyzed source revision plus dirty-working-tree fingerprint, component keys, task/analysis IDs and gate results without secrets. Any source change after analysis requires fresh analysis before goal completion. If initial analysis is red, report provisioning/configuration separately from quality readiness and keep the Sonar setup goal incomplete; propose only goal-scoped fixes rather than silently fixing unrelated legacy debt.

The project instruction saved before initial analysis points to the project/component configuration and the [canonical quality gate rule](../../assets/global-stack-policy.md#sonarqube-quality-gates). That durable configuration, not a cached readiness flag, activates enforcement on subsequent goals unless the user explicitly sets `evaluation.sonarqube.enabled=false` in `kiss-chris-stack.config.json`. While enabled, configuration remains active when the container is stopped, `.env` is missing or credentials expire; fail visibly until restored. Do not infer opt-out from removed credentials. Report what was actually verified and any remaining limits. Actual container provisioning, login, scanner integration and gate behavior need a live run on the target host; do not claim them from this skill's existence.
