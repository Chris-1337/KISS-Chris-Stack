# KISS-Chris-Stack setup

Prepare local tooling and documentation before the original implementation `/goal`. This setup bootstrap is exempt from that goal gate: do not create another goal, launch implementation agents, or invoke setup recursively. Sub-agents receive only their assigned role. Existing permissions and project rules still apply.

## Project selection and initialization marker

Plugin installation uses [onboarding](../onboarding/SKILL.md) first, before any setup/readiness/repair. Wait for consent and the explicit existing project path; never substitute the installation `cwd`. A declined or pending onboarding dialogue must not fall through to automatic project setup.

Use only project-root `kiss-chris-stack.config.json` as the initialization marker. After resolving installation onboarding, run `python "<plugin-root>/scripts/evaluation-config.py" --project "<project-root>" --update` before runtime readiness in an existing project. Use the actual Python interpreter and execute the root hook's supplied argv as arguments, never as shell-evaluated text. The updater validates configuration and adds only missing current defaults while preserving every explicit workflow/evaluation value; it does not initialize an absent file. Complete configuration retains its bytes and mtime. Invalid, malformed, unreadable or unsafe nonregular/symlink update targets block setup without replacement; never replace errors with defaults. Without `--update`, the resolver remains read-only and supplies `plan-mode=false` and enabled evaluation defaults when absent. Do not execute the updater for pending or declined installation onboarding, or in delegated roles.

For an ordinary root task with a configuration, run the runtime-readiness section only; do not reinitialize the project or invoke documentation bootstrap merely because `docs/` or `agent-traces/` is missing/empty. Without the root configuration, run runtime readiness, documentation bootstrap, then initialization completion below. An explicit `/setup` also fills documentation gaps in an already configured project. Documentation contents and cached ready flags never determine initialization.

## Runtime readiness, every root task

1. Resolve the plugin root from this loaded skill's location (`../..`), not a fixed user/cache path or a different loose skill with the same name. Read [versions.json](../../assets/versions.json) and [the shared policy](../../assets/global-stack-policy.md). Require Node.js, Python 3.10+ and the Codex CLI. If the bootstrap interpreter is unavailable, report how to install it on this host and require reload; do not claim hooks ran when Node was missing.
2. Run `python "<plugin-root>/scripts/setup-runtime.py" --project "<project-root>"` (use the actual Python executable). This performs current, read-only checks: CLI versions, pinned CodeGraph npm package, bundled-resource hashes, an actual bundled UIUX search, global policy plus an existing override, CodeGraph index/status and MCP registration. The helper disables CodeGraph network fallback and Python bytecode writes during checks. Use the output as evidence, not a cached receipt.
3. If checks fail, an explicit `/setup`, accepted onboarding with a validated project path, or an ordinary root lifecycle instruction authorizes necessary local setup/repair: run the same command with `--repair`, then repeat the check. Repair installs the pinned CodeGraph npm package when missing/outdated and official RTK binaries only after SHA256 verification; it writes only the marker-owned global policy (and existing `AGENTS.override.md`), registers missing CodeGraph MCP and initializes/synchronizes the intended index. Preserve foreign configuration. Do not overwrite conflicting MCP entries, auto-trust hooks or bypass host approval; report the exact conflict. No external resource provisioning is authorized. `--repair` may download dependencies and therefore needs the normal network permissions of the host.
4. `runtime_ready=true` / exit 0 means executable runtime checks passed; `ready` deliberately remains false and `session_verification_required=true`. A script cannot inspect this session's actual tool availability. Invoke the real CodeGraph MCP status/context tool in this session for the intended project. Only runtime success **and** a successful live tool call establish overall readiness. If tools are absent, label `reload-required`, have the user reload the host, and recheck. Runtime failures return nonzero and require repair, not a blind reload loop. Never use a ready flag or a CLI registration as a substitute.
5. Verify Node/Python/RTK/CodeGraph visibility in the agent's own shell after repair. RTK is installed under the user's `.local/bin`; add that directory to the current shell PATH when necessary and request host reload if the process environment is stale. Do not silently change persistent PATH, credentials or hook trust.
6. Review/trust the packaged lifecycle hook definition through the host's normal UI once; that user decision is required for hooks to execute. Changing hook definitions can require renewed review. No unconditional automation is promised while the plugin is disabled, hooks untrusted/unloaded, Node unavailable, or MCP not reloaded.

## Documentation bootstrap

Write documentation in English, including new bootstrap documents and goal traces, following the [shared language policy](../../assets/global-stack-policy.md#language).

1. Inspect the project root, repository instructions, existing `docs/` and `agent-traces/`, component boundaries, relevant code/tests/configuration, and available designs. Read relevant existing documents before writing; do not scan secrets or dependency/build output.
2. Create missing `docs/` and `agent-traces/` directories with native file tools. Create missing `agent-traces/user-feedback/` and its generic README protocol for recording and reviewing scoped feedback, using the [feedback protocol](../../agent-traces/user-feedback/README.md); copy only the protocol, never this plugin repository's feedback records. Preserve existing feedback and its README; do not invent feedback. Ignore generated tool/VCS metadata such as `.codegraph/` when deciding whether the project has actual application content. In an empty project, create only the directory structure and generic feedback protocol (use `.gitkeep` if Git must retain empty directories); do not invent components, architecture, decisions, or goals.
3. In an existing project, create missing `agent-traces/<component>/` subdirectories for real components. Add only missing, evidence-backed documentation under `docs/`: system architecture covering every existing component and its interactions (including frontend/backend when present), known business decisions, and technical decisions as ADRs when their rationale is established. Link the code/design or user decision that supports a claim. Mark uncertain facts and questions explicitly; never fabricate historical decisions or completed goal traces.
4. Preserve existing files and their content. Reuse their layout; add missing coverage in a new document or make a narrow additive edit only where content is absent. A repeated run must not duplicate or rewrite existing documentation. Placeholder-only folders count as empty, but do not repeatedly create the same placeholders in an empty project.
5. `docs/` is human documentation. `agent-traces/<component>/` is long-term agent memory: after actual goal implementation, write a short goal note containing what changed, why, affected locations, checks/results, and remaining limits. Do not copy chats, raw logs, or secrets, and do not backfill fictitious traces during bootstrap.
6. Report created files, evidence, and missing information. Ask the user about unresolved requirements or necessary decisions before dependent implementation; keep unknowns explicit. Return to context collection and goal definition only after this bootstrap, without calling setup again in the same preparation pass.

## Initialization completion

Create missing project-root `kiss-chris-stack.config.json` only after successful runtime readiness, a real session CodeGraph MCP call and completed documentation bootstrap. Failed, interrupted or reload-required prerequisites must leave the marker absent. Write the resolver's validated default JSON (`plan-mode=false`, `evaluation.live.enabled=true` and `evaluation.sonarqube.enabled=true`) with exclusive creation, such as Python `open(path, "x", encoding="utf-8")`; never truncate or overwrite an existing file. If a concurrent setup created it, validate that file through the resolver and preserve its settings instead. On write failure, remove only this attempt's incomplete new file after confirming its identity is unchanged; preserve pre-existing/concurrent configuration. An abrupt process interruption during the final write can leave an invalid file: strict validation blocks completion until it is safely repaired, never treat it as absent or ready. Re-read the written configuration through the resolver before reporting initialization complete. The read-only runtime checker and evaluation resolver, including its existing-file `--update` mode, never create the marker themselves. Optional SonarQube consent is separate from normal initialization success.

## Optional SonarQube after setup

After explicit onboarding or `/setup` completes, check optional container prerequisites with `python "<plugin-root>/skills/setup-sonarqube/scripts/check-container-runtime.py"`. Read its JSON `available` flag; this read-only optional probe never changes runtime readiness. If SonarQube is already configured for this project, validate its configuration and apply the shared quality gate rule instead of offering another installation.

If a reachable Linux engine is available, ask whether the user also wants to run the bundled [setup-sonarqube](../setup-sonarqube/SKILL.md). Wait for consent before starting containers, creating accounts/tokens or changing project configuration. A declined offer leaves normal setup complete; defer it until another explicit `/setup` or `/setup-sonarqube` request. Do not repeat the offer during the mandatory per-task readiness recheck. If prerequisites are unavailable, only explain that `/setup-sonarqube` can run later after installing Docker Desktop, Rancher Desktop, Podman or another compatible Linux runtime (or starting/fixing the existing engine); continue normal setup. Docker is optional.

Automatic entry: trusted SessionStart/UserPromptSubmit hooks inspect the root configuration for ordinary project tasks: missing means initialization; present means validate/backfill missing defaults through `evaluation-config.py --update`, then current runtime/MCP readiness without repeated project initialization. The hook emits argv for the root to execute after onboarding routing; the bare hook remains read-only. Installation onboarding has priority over this routing, including its consent/path replies. Explicit `/setup` fills documentation gaps even when configuration exists. Proceed to the original user request through the stack only after readiness, context collection and necessary clarifications. Setup alone grants no permission for external writes or SonarQube provisioning.
