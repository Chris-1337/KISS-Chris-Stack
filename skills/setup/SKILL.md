# KISS-Chris-Stack setup

Prepare local tooling and documentation before the original implementation `/goal`. This setup bootstrap is exempt from that goal gate: do not create another goal, launch implementation agents, or invoke setup recursively. The root coordinates and delegates setup execution, factual context research and documentation roles during bootstrap without an implementation goal. Delegated preparation runs assigned commands only; it never initiates root setup recursively. All pure context collection uses fresh `gpt-6-luna` low-reasoning agents with no inherited context, facts-only notes, no source/config changes or design decisions and no silent model/effort substitution; final documentation/editing is a separate role. Root retains lifecycle gates and the actual session MCP call. Sub-agents receive only their assigned role. Existing permissions and project rules still apply.

## Project selection and initialization marker

For ordinary software tasks, the [orchestrator](../kiss-chris-stack/SKILL.md) selects the route before setup: tiny bounded low-risk delegated direct work skips setup/goal/triad overhead. The sections below apply to stack routes and explicit setup/onboarding, not automatic initialization for every minimal edit.

Plugin installation uses [onboarding](../onboarding/SKILL.md) first, before any setup/readiness/repair. Wait for consent and the explicit existing project path; never substitute the installation `cwd`. A declined or pending onboarding dialogue must not fall through to automatic project setup.

## Required storage choice

For first-time initialization and every explicit `/setup`, the root must ask the user for the Wayfinder storage choice: local Markdown, GitHub or GitLab. Read an existing configuration read-only and display its current provider/location, offering to keep or change it. Collect or confirm the local directory or hosted repository/project target. Local `.scratch` may be recommended; defaults are not consent, and neither an existing/backfilled value, a preselected option, silence nor elapsed time answers the question.

Wait for an actual user answer before dependent configuration, tracker or documentation writes, including configuration backfill and helper `--prepare`. Retain answers already explicitly supplied in the same setup dialogue; do not ask an answered question again or add a closing confirmation. Pending/declined onboarding still takes priority. Invalid existing configuration blocks without replacing it with defaults.

Ordinary per-task readiness reuses the validated current selection without another prompt. It is not explicit setup; tiny direct tasks still skip setup entirely. This conversational choice gate belongs to setup, not to the noninteractive preparation/check helper.

## Configuration marker and preparation

For first-time initialization and explicit `/setup`, after the required storage choice is answered, perform the preparation in [Git hygiene and staging](#git-hygiene-and-staging) before the first project mutation, including runtime repair or configuration backfill. Finalize staging only after the setup checks below succeed. Ordinary per-task readiness/backfill does not run this Git workflow.

Use only project-root `kiss-chris-stack.config.json` as the initialization marker. After resolving installation onboarding and, for first/explicit setup, the required storage choice, run `python "<plugin-root>/scripts/evaluation-config.py" --project "<project-root>" --update` before runtime readiness in an existing project. If the user changed an existing selection, first delegate a validated atomic update of only its tracker fields using the existing concurrency-safe configuration utilities; preserve all other settings. Never use pending stdin settings to override an existing marker. Use the actual Python interpreter and execute the root hook's supplied argv as arguments, never as shell-evaluated text. The updater validates configuration and adds only missing current defaults while preserving every explicit workflow/evaluation value; it does not initialize an absent file. Complete configuration retains its bytes and mtime. Invalid, malformed, unreadable or unsafe nonregular/symlink update targets block setup without replacement; never replace errors with defaults. Without `--update`, the resolver remains read-only and supplies `grill-me=true`, `grill-with-docs=true`, `wayfinder=true`, `plan-mode=false` and enabled evaluation defaults when absent. Do not execute the updater for pending or declined installation onboarding. Only the root or its explicitly assigned setup/preparation worker executes the supplied updater argv; researchers, test, implementation and evaluation roles do not initiate setup or updates.

For an ordinary root task with a configuration, run the runtime-readiness section only, followed by the required configured Wayfinder binding below; do not reinitialize the project or invoke documentation bootstrap merely because `docs/` or `agent-traces/` is missing/empty. Without the root configuration, run runtime readiness, documentation bootstrap, then initialization completion below. An explicit `/setup` also fills documentation gaps in an already configured project. Documentation contents and cached ready flags never determine initialization.

## Runtime readiness, every root task

1. Resolve the plugin root from this loaded skill's location (`../..`), not a fixed user/cache path or a different loose skill with the same name. Read [versions.json](../../assets/versions.json) and [the shared policy](../../assets/global-stack-policy.md). Require Node.js, Python 3.10+ and the Codex CLI. If the bootstrap interpreter is unavailable, report how to install it on this host and require reload; do not claim hooks ran when Node was missing.
2. Run `python "<plugin-root>/scripts/setup-runtime.py" --project "<project-root>"` (use the actual Python executable). This performs current, read-only checks: CLI versions, pinned CodeGraph npm package, bundled-resource hashes, an actual bundled UIUX search, global policy plus an existing override, CodeGraph index/status and MCP registration. The helper disables CodeGraph network fallback and Python bytecode writes during checks. Use the output as evidence, not a cached receipt.
3. If checks fail, an explicit `/setup`, accepted onboarding with a validated project path, or an ordinary root lifecycle instruction authorizes necessary local setup/repair: run the same command with `--repair`, then repeat the check. Repair installs the pinned CodeGraph npm package when missing/outdated and official RTK binaries only after SHA256 verification; it writes only the marker-owned global policy (and existing `AGENTS.override.md`), registers missing CodeGraph MCP and initializes/synchronizes the intended index. Preserve foreign configuration. Do not overwrite conflicting MCP entries, auto-trust hooks or bypass host approval; report the exact conflict. No external resource provisioning is authorized. `--repair` may download dependencies and therefore needs the normal network permissions of the host.
4. `runtime_ready=true` / exit 0 means executable runtime checks passed; `ready` deliberately remains false and `session_verification_required=true`. A script cannot inspect this session's actual tool availability. Invoke the real CodeGraph MCP status/context tool in this session for the intended project. Runtime success **and** a successful live tool call establish runtime/MCP readiness; overall stack readiness additionally requires the configured Wayfinder binding below. If tools are absent, label `reload-required`, have the user reload the host, and recheck. Runtime failures return nonzero and require repair, not a blind reload loop. Never use a ready flag or a CLI registration as a substitute.
5. Verify Node/Python/RTK/CodeGraph visibility in the agent's own shell after repair. RTK is installed under the user's `.local/bin`; add that directory to the current shell PATH when necessary and request host reload if the process environment is stale. Do not silently change persistent PATH, credentials or hook trust.
6. Review/trust the packaged lifecycle hook definition through the host's normal UI once; that user decision is required for hooks to execute. Changing hook definitions can require renewed review. No unconditional automation is promised while the plugin is disabled, hooks untrusted/unloaded, Node unavailable, or MCP not reloaded.

## Configured Wayfinder tracker

After runtime/MCP readiness and the required first/explicit setup answer, delegate the tracker preparation/check to the setup worker. The authoritative project setting is `wayfinder-tracker`, independent of the Boolean `wayfinder`: local `{ "provider": "local", "directory": ".scratch" }` by default; GitHub `{ "provider": "github", "repository": "OWNER/REPO" }`; GitLab `{ "provider": "gitlab", "project": "https://HOST/GROUP/PROJECT" }`. No credentials or arbitrary adapters belong here. Preserve the user's answered choice; never infer/redirect the backend from a Git remote or silently fall back when the selected provider fails.

For an existing marker, after validated default backfill and runtime/MCP proof, execute the bundled helper as an argument array:

```text
python <plugin-root>/scripts/setup-wayfinder.py --project <project-root> --prepare
python <plugin-root>/scripts/setup-wayfinder.py --project <project-root> --check
```

Both commands must succeed before reporting stack readiness or using Wayfinder. This targeted reconciliation creates the selected local root and managed `docs/agents/issue-tracker.md` only; it is not documentation bootstrap or native `/init`. It creates no effort, map or ticket. Ordinary readiness does not stage files. A changed backend/directory reconciles its owned operations block and preserves old ticket data; it never migrates or deletes it. An unchanged binding preserves bytes/mtime and surrounding user content; an unmanaged, malformed or unsafe target blocks without overwrite. Use the [tracker setup skill](../setup-matt-pocock-skills/SKILL.md) for explicit backend changes.

For first-time initialization with no marker, resolve full pending settings in memory, including the user's chosen provider/target and all workflow/evaluation values. Delegate the helper's `--prepare --config-stdin` and `--check --config-stdin` modes with that full validated JSON on stdin, not a shell string or temporary initialization marker. A present/concurrently appearing marker must agree with those resolved settings; conflicts block without replacement. After runtime/MCP, tracker, documentation and native-init success, create the final marker last with exactly those selected resolved settings, then re-read the ordinary resolver and helper `--check`. Do not reset a custom first-init target to local defaults or claim success from stale binding evidence.

The helper checks existing path components for symlinks/junctions/reparse points and local targets stay within the project. Hosted selections require existing native `gh`/`glab`, authenticated read-only identity/Issues/unarchived/access metadata checks and explicitly configured host/target. Missing CLI, invalid target or unavailable authentication blocks; do not install/login automatically or infer a local fallback. GitHub requires visible TRIAGE-or-higher and GitLab Developer-or-higher for this bundled label/claim protocol; lower roles may create individual issues but do not satisfy this setup. Read-only metadata is not a token-write guarantee or permission to create issues, labels, assignments or comments. External writes remain separately authorized. Configuration contains target strings, not secrets or executable commands.

## Documentation bootstrap

Write documentation in English, including new bootstrap documents and goal traces, following the [shared language policy](../../assets/global-stack-policy.md#language).

1. Assign factual project exploration to the designated Luna-low context agents: project instructions, `docs/`, `agent-traces/`, component boundaries, relevant code/tests/configuration and designs. A separate documentation role uses their referenced facts for the edits below. Do not scan secrets or dependency/build output.
2. Create missing `docs/` and `agent-traces/` directories with native file tools. Create missing `agent-traces/user-feedback/` and its generic README protocol for recording and reviewing scoped feedback, using the [feedback protocol](../../agent-traces/user-feedback/README.md); copy only the protocol, never this plugin repository's feedback records. Preserve existing feedback and its README; do not invent feedback. Ignore generated tool/VCS metadata such as `.codegraph/` when deciding whether the project has actual application content. In an empty project, create only the directory structure and generic feedback protocol (use `.gitkeep` if Git must retain empty directories); do not invent components, architecture, decisions, or goals.
3. In an existing project, create missing `agent-traces/<component>/` subdirectories for real components. Add only missing, evidence-backed documentation under `docs/`: system architecture covering every existing component and its interactions (including frontend/backend when present), known business decisions, and technical decisions as ADRs when their rationale is established. Reuse the existing system overview's name and location; default to `docs/architecture.md` when absent. Link the code/design or user decision that supports a claim. Mark uncertain facts and questions explicitly; never fabricate historical decisions or completed goal traces.
4. After creating or reusing the system architecture, complete [module research and synthesis](#module-research-and-synthesis) for every real module. Empty projects skip module research; do not invent modules or launch research agents for them.
5. Preserve existing files and their content. Reuse their layout; add missing coverage in a new document or make a narrow additive edit only where content is absent. A repeated run must not duplicate or rewrite existing documentation. Placeholder-only folders count as empty, but do not repeatedly create the same placeholders in an empty project.
6. `docs/` is human documentation. `agent-traces/<component>/` is long-term agent memory: after actual goal implementation, write a short goal note containing what changed, why, affected locations, checks/results, and remaining limits. Do not copy chats, raw logs, or secrets, and do not backfill fictitious traces during bootstrap.
7. After all documentation, including module synthesis, complete [native initialization and project instructions](#native-initialization-and-project-instructions). This final bootstrap step also applies to empty projects, without inventing architecture or components.
8. Report created files, evidence, and missing information. Ask the user about unresolved requirements or necessary decisions before dependent implementation; keep unknowns explicit. Return to context collection and goal definition only after this bootstrap, without calling setup again in the same preparation pass.

### Module research and synthesis

1. **Map modules:** the root assigns module inventory preparation from the factual system overview and source notes to a documentation role, then reviews actual logical module boundaries, not one module per arbitrary directory. Record a module inventory in the overview: module, allowed module-local source/test/configuration paths, and notes destination. Reuse existing documentation folders; otherwise use a distinct stable `docs/<module>/` folder per module. Exclude secrets, dependencies, generated files and VCS/tool metadata from research paths.
2. **Dispatch:** for each documentation-bootstrap run, launch one dedicated research sub-agent per module using GPT-6 Luna (`model="gpt-6-luna"`, `reasoning_effort="low"`, `fork_turns="none"` or equivalent fresh context). Supply the module name, allowed paths, existing module documentation, notes destination and all relevant instructions directly; do not inherit the parent conversation or unrelated project context. Respect available concurrency slots and process all modules in batches when needed. Existing architecture or notes do not skip this dispatch: researchers validate and reuse still-current notes without rewriting them. When resuming the same interrupted bootstrap, validate completed research against its sources and resume only missing or incomplete module research.
3. **Collect notes only:** each researcher reads only the assigned module's allowed paths and writes only its assigned `docs/<module>/research-notes.md` (or existing equivalent). Collect purpose, responsibilities, entry points/interfaces, internal flow, data/configuration, tests, and dependencies visible within that module. Include source links and the inspected source revision plus dirty-source fingerprint, or inspected file hashes, distinguish observations from uncertain facts and open questions, and retain these notes under `docs/`. Record outgoing imports/references as seen locally; do not inspect or traverse other modules to explain their behavior. Do not make source edits or implementation changes, curate final architecture, run setup, register goals, or spawn recursive agents. Preserve existing notes and add only missing evidence; never include secrets or raw logs.
4. **Synthesize:** wait for all module research agents to finish successfully. The root reviews the inventory and source-linked notes, assigns any missing/stale fact checks to the researchers, then delegates synthesis to a separate documentation agent that resolves supported overlaps/conflicts and writes coherent module architecture and documentation from the notes. Root review verifies scope, source pointers and that cited revisions plus dirty-source fingerprints, or inspected file hashes, remain current before accepting synthesis. Stale evidence requires renewed research for the affected module before synthesis. Default to `docs/<module>/architecture.md` for structure, flow, interfaces and dependencies, and `docs/<module>/README.md` for purpose, usage, configuration and verification; reuse existing documents/layout instead of creating equivalents. Link module documentation and retained research notes from the system overview, and link module architecture back to that overview. Describe cross-module interactions only when supported by the collected evidence; keep unresolved details explicit.
5. **Completion and failure:** unavailable agents, the requested model or reasoning setting are visible blockers; never substitute a different model or effort or fall back silently. Failed, interrupted, out-of-scope or incomplete research blocks documentation-bootstrap completion, creation of a missing initialization marker and final setup staging. Report affected modules and preserve valid notes/documents; retry or resume remaining module research before synthesis and successful completion. An existing initialization marker remains intact. The root reports created/reused files and remaining unknowns without claiming unobserved behavior or future model compliance.

### Native initialization and project instructions

1. **Run native `/init`:** after documentation and module synthesis finish, the root invokes the host-native `/init` command in the selected project directory for first-time initialization and explicit `/setup`. This phase never runs during ordinary readiness, delegated roles, or pending/declined onboarding. Snapshot existing project-root `AGENTS.md` bytes and its Git state before dispatch, alongside relevant inherited, nested and `AGENTS.override.md` instruction scopes. Reject symlink/nonregular output targets. Never delete existing `AGENTS.md` to force `/init` regeneration or force an overwrite; if native `/init` refuses or is a no-op because the file exists, reuse that file for review.
2. **Require actual dispatch:** use the host's supported native command mechanism; do not invent a shell command such as `codex init`, send `/init` through `codex exec`, or treat printing the command as execution. If native dispatch is unavailable, explain that setup is pending, ask the user to run `/init` in the intended project directory, and resume review after the native result is available. Do not claim `/init` completed without execution evidence. Unavailable, failed or interrupted dispatch/review blocks setup completion, creation of a missing initialization marker and final staging; preserve any existing marker and valid files.
3. **Delegate optimization, review in the root:** assign a documentation agent the native result, existing guidance and collected evidence to review and edit project-root `AGENTS.md` into concise, actionable English instructions. The root reviews the resulting evidence and preserved instructions before accepting it. Preserve unique valid project-specific guidance, conventions, commands and constraints; retain security/permission requirements and managed blocks unchanged. Preserve explicit user requirements as authoritative guidance even when implementation is pending. Remove duplicated inherited global/stack rules only where equivalent guidance is actually inherited, generic boilerplate, copied architecture/documentation prose and stale or unsupported factual claims after evidence verification. Link canonical `docs/` and `agent-traces/` context, including actual architecture/module documents when present, instead of duplicating them. In empty projects, keep only truthful minimal guidance and existing context links; invent no commands, components or decisions. Preserve global, nested and override files; report when `AGENTS.override.md` shadows this file or another instruction scope changes effective precedence, without modifying those files to bypass it.
4. **Verify and finish:** compare against the pre-init snapshot and actual project sources so unique valid instructions survive generation and optimization, links resolve and commands are evidenced. Repeated runs with unchanged evidence must not rewrite the file or duplicate instructions; reuse existing good content. Confirm a regular nonempty project-root `AGENTS.md` exists and report native dispatch/refusal, reviewed changes and any unresolved instruction conflict before marker creation and setup staging. Use only the exact nonsecret file as a candidate under the shared Git rules; pre-existing mixed work keeps its index entry unchanged.

Native behavior and instruction precedence are documented in [developer commands](https://learn.chatgpt.com/docs/developer-commands?surface=cli) and [AGENTS.md configuration](https://learn.chatgpt.com/docs/agent-configuration/agents-md). Host support must be checked in the current session; these instructions do not provide their own command dispatcher.

## Initialization completion

Create missing project-root `kiss-chris-stack.config.json` only after successful runtime readiness, a real session CodeGraph MCP call and completed documentation bootstrap, including the configured tracker, native `/init` and root review/optimization of project instructions. Failed, interrupted or reload-required prerequisites must leave the marker absent. Write the exact full validated pending settings used by tracker preparation, including the selected `wayfinder-tracker` and all workflow/evaluation values (defaults only where omitted), with exclusive creation, such as Python `open(path, "x", encoding="utf-8")`; never truncate or overwrite an existing file. If a concurrent setup created it, validate and preserve it, compare its resolved settings against the pending selection and block on mismatch; never report a prepared backend that differs from the actual marker. On write failure, remove only this attempt's incomplete new file after confirming its identity is unchanged; preserve pre-existing/concurrent configuration. An abrupt process interruption during the final write can leave an invalid file: strict validation blocks completion until it is safely repaired, never treat it as absent or ready. Re-read the written configuration through the resolver and require the tracker helper `--check` against it before reporting initialization complete. The read-only runtime checker and evaluation resolver, including its existing-file `--update` mode, never create the marker themselves. Optional SonarQube consent is separate from normal initialization success.

After successful initialization, or successful explicit `/setup` in an existing project, finish [Git hygiene and staging](#git-hygiene-and-staging) before reporting completion and before offering optional SonarQube. A later SonarQube failure does not undo this completed normal setup.

## Git hygiene and staging

This is the shared agent-executed Git workflow for first-time initialization, explicit `/setup`, and authorized `/setup-sonarqube`. It automatically updates local ignore rules and stages the setup's nonsecret project files without another confirmation. Do not run this preparation or staging for ordinary per-task readiness checks, configuration backfill, evaluation or token renewal.

1. **Before mutation:** work in the selected project directory and establish whether it is inside a Git worktree, using `git rev-parse --show-toplevel`. For a worktree, record a baseline of existing files and their working-tree/index state, using `git status --porcelain=v1 -z --untracked-files=all` and `git ls-files --stage -z`; retain original bytes for files setup will edit. Track the exact files created or changed by this invocation, including `.gitignore`. Resolve paths within the selected project; reject symlink/nonregular ignore files and output targets rather than following them. Preserve unrelated files and index entries. A Git failure other than an established non-Git directory is an error, not permission to assume a fresh repository.
2. **Ignore before creation:** append only missing project-root rules to `.gitignore`: `/.codegraph/` for normal setup; for SonarQube, `/.env`, `/.scannerwork/` and `/.sonar-evidence/`. Add a rule only for an artifact that this workflow uses. Preserve existing bytes, comments, newline style and rules; do not duplicate rules on reruns. In Git, use `git ls-files` with literal paths to detect tracked local artifacts, then run `git check-ignore -- <exact-artifact-path>` separately for every artifact to prove effective exclusion, including applicable child paths and conflicting negations; an aggregate success for several paths proves only that at least one is ignored. Before writing secrets or credentials, `.env` must be untracked and effectively ignored. Tracked local artifacts are a conflict: stop the affected writes and report paths without their contents; ignore rules do not protect tracked files. Never automatically untrack files, remove conflicting user rules, or force-add ignored files. Treat unexpected Git errors as failures. Keep necessary ignore protection even if later setup fails.
3. **Select only owned changes after success:** finish runtime/MCP, documentation, native `/init` with root instruction review and configuration validation for normal setup; finish the required analysis/readback/gate checks for SonarQube before staging its files. Failed or interrupted setup does not stage partial output. Eligible exact files are the changed `.gitignore`, `kiss-chris-stack.config.json`, project-root `AGENTS.md`, files actually created or updated under `docs/` and `agent-traces/`, and actual nonsecret Sonar scanner/build/Compose configuration such as `sonar-project.properties` or the project instruction enabling its gate. Inspect candidate diffs for credentials before adding them. Exclude secrets, local indexes, scanner output, evidence, caches and logs. A directory name is not an add target. Never use broad staging such as `git add .`, `git add -A`, directory adds or wildcards.
4. **Preserve mixed work:** if a candidate had pre-existing staged, unstaged or untracked content, or concurrent unrelated edits, skip its whole-file add and report it as left unstaged by setup; leave its existing index entry unchanged. This includes partially staged `.gitignore`, `AGENTS.md`, documentation and build files. Do not overwrite or reset the user's staging to isolate setup hunks. For newly created files and previously clean files containing only this invocation's changes, run `git --literal-pathspecs add -- <exact-setup-files>` as an argument array, with each validated file as a separate argument. Never force staging, commit, push or run `git init`.
5. **Verify and report:** compare the final index with the baseline, proving that only selected setup files were added/updated and unrelated staged entries are unchanged. Recheck local artifact exclusions. Report staged paths, deliberately skipped mixed/ignored files and any Git failure without secret contents; do not claim staging succeeded after an error. Leave valid configuration and protected local data intact when staging fails. On reruns, unchanged files and existing rules need no write or add; a previously interrupted run's pre-existing files follow the same conservative mixed-work rule. In non-Git projects, maintain the future `.gitignore` rules, protect secrets with owner-only permissions, skip staging and explain why; never initialize a repository automatically. Git absent or unusable must be reported explicitly rather than presented as successful staging.
