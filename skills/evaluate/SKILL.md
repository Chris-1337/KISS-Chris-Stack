# Evaluate the running project

The root resolves configuration before defining the goal and supplies it to the separate evaluation agent. That agent re-reads it before completion using `python "<plugin-root>/scripts/evaluation-config.py" --project "<project-root>"`. Follow the [shared policy](../../assets/global-stack-policy.md); do not register another goal or run setup in a delegated role.

## Configuration and acceptance

Read only project-root `kiss-chris-stack.config.json`. This file also marks project initialization; [setup](../setup/SKILL.md) creates a missing file only after successful initialization and preserves an existing one. Without `--update`, the resolver is read-only: it emits top-level `grill-me`, `grill-with-docs` and `wayfinder` (each default `true`), `plan-mode` (default `false`), `evaluation.live.enabled` and `evaluation.sonarqube.enabled` (both default `true`) when the file or settings are absent, without marking a project initialized. Workflow/evaluation switches accept only JSON booleans; the separate `wayfinder-tracker` accepts only its strict provider-specific string fields. invalid JSON, duplicate/unknown keys, invalid types, an unreadable file or a missing project block evaluation. Never treat a parse/read error as an opt-out. This file contains workflow/evaluation switches and a Wayfinder target, never shell commands, credentials or application startup configuration. Before readiness on an initialized stack root task, the root assigns execution of the hook-provided `--update` argv to add only missing current defaults in a valid existing file; explicit values remain unchanged. Evaluation and other delegated roles use the read-only invocation; only an explicitly root-assigned setup/preparation worker may execute the supplied updater argv.

`plan-mode` controls the root's stack-goal approval step under the [shared policy](../../assets/global-stack-policy.md): false continues automatically; true presents the strong registered goal, requests explicit user approval and yields before dispatching any test, implementation or evaluation role. Resume the same goal only after approval. Independent strict `grill-with-docs` and `wayfinder` booleans default to `true`, enabling their selected unclear/large automatic routes; clear normal work uses stack with goal, and tiny bounded fixes use the delegated direct route before setup. Legacy `grill-me` defaults `true` but remains for explicit invocation, not an additional automatic interview. Explicit requests remain available when automatic switches are false. Disabled selected skills never authorize unresolved decisions. Interviews continue automatically without a closing confirmation when settled; they never replace goal approval. These switches do not change the host collaboration mode or disable evaluation gates for stack work.

The root delegates substantive work, including documentation, to the appropriate separate roles. All pure information collection goes exclusively to fresh `gpt-6-luna` low-reasoning agents with no inherited context, source-linked facts/notes only and no implementation/design decisions. Evaluation source inspection and evidence-based judgments remain part of the separate evaluator role. Root schedules all dependency-ready Wayfinder ticket phases within host slots and isolated write ownership, keeps blocked tickets pending, and verifies integrated source. Only root owns native goals; one-active-goal hosts use explicitly textual/unregistered strong child ticket goals under the native umbrella.

For either evaluation gate, an explicit `false` skips that gate independently; record **disabled/skipped**, not passed. Never change a switch to evade a failure. The user can deliberately enable/disable either gate through this file. Configuration changes after goal definition require revisiting acceptance and rerunning affected checks; there is no cached approval. `sonarqube.enabled=true` enforces existing configured projects and does not authorize provisioning SonarQube in unrelated projects. With `false`, skip scanner/readback/token operations while preserving service configuration, credentials and data. With `true` and a configured project, run [setup-sonarqube](../setup-sonarqube/SKILL.md)'s renewal preflight and require fresh current-source analysis-specific green quality gates for all relevant components. Missing credentials/services/coverage and failed/pending analyses block completion.

Require the authoritative `wayfinder-tracker` binding through bundled `scripts/setup-wayfinder.py --check` before evaluating tracker use. Local directory/map/ticket operations must use its actual configured directory; hosted preflights pin explicit host/identity and require Issues/unarchived/visible role metadata without external writes. No unavailable selected backend may silently fall back to local. For first-init proof, validate full pending settings via `--config-stdin`, keep the marker absent until all setup success, then recheck exact selected marker settings. Preserve existing documents, old tickets and direct-route boundaries. Read-only hosted metadata is not token-write proof.

## Live functional proof

When `live.enabled=true`, prove the affected functionality in the actual running project using its existing startup commands and configuration. Start it directly or with `docker compose` from the intended working tree; build/recreate affected containers as necessary so stale images cannot supply evidence. Reuse a running instance only after proving its identity and source fingerprint match the evaluated working tree. Inspect the engine endpoint before use: local test authorization does not grant writes to remote engines or production systems.

1. Determine affected components and behavior from the goal, call paths and existing tests. Use safe local test data and the project's existing integration environment; do not invent another application or expose real data. Record revision and dirty-source fingerprint, resolved switches, runtime versions, startup command, working directory and target identity without secrets.
2. Start the necessary actual components and poll readiness with bounded startup/request timeouts. Keep startup failures visible. A process existing or a successful health request alone does not prove functionality: execute the affected workflow and assert its expected outputs, state changes and applicable error behavior. Exercise backend/API/CLI/plugin functionality through its real interface when there is no frontend. Documentation-only work needs applicable document/contract checks, with runtime checks marked inapplicable and explained; do not fabricate a live application.
3. For affected frontend functionality, a real browser and/or Playwright test is mandatory. Open the running application, interact with the changed user flow and assert user-visible results, including relevant validation/error states. Inspect browser console/network failures and capture useful screenshots/traces or assertion output. Unit tests, mocks, static HTML inspection and screenshots without behavioral assertions do not replace this proof.
4. When live frontend evaluation is active, automatically install missing test dependencies, including Playwright CLI and a compatible headless Chromium browser, without another confirmation. Reuse existing project runners, pinned versions and browser caches first; preserve manifests and lockfiles unless the goal needs a project dependency. Otherwise use an isolated tool installation/cache. Check Node/npm and the selected CLI's `--help`/version first. The official [CLI installation guide](https://playwright.dev/agent-cli/installation) documents `npm install -g @playwright/cli@latest`, or cache-backed `npx --yes --package @playwright/cli playwright-cli --help`; reuse the same resolved version for installation and execution. For versions exposing it, `playwright-cli install-browser` installs matching browsers; `--with-deps` installs needed Linux system libraries. For an existing Playwright runner, use its matching `playwright install chromium` (with `--with-deps` on Linux when needed), as described in [browser installation](https://playwright.dev/docs/browsers). Check supported options and select headless Chromium explicitly; verify a real launch and workflow assertions, not installation exit codes alone. Install required local prerequisites within host permissions; network, privilege or browser-launch failures remain visible blockers rather than skipped frontend tests. Do not change global security settings or bypass host approval.
5. When there is no frontend, no affected frontend behavior, or live evaluation is disabled, skip browser dependency installation. Record the applicability decision. Disabled live checks do not disable ordinary goal tests or SonarQube.
6. Record executable evidence: commands, exit codes, target identity, assertions/results, source fingerprint and artifact paths without secrets. Source changes after evaluation require fresh affected proof. Failed startup, unavailable required dependencies, unreachable components or failing assertions block completion while the gate is enabled.
7. In cleanup, stop only owned processes, browser sessions and containers started for this evaluation; preserve reused services and data. Never delete volumes, run `down -v` or prune. Report cleanup failures and remaining resources.

The evaluator reports each gate as passed, failed, disabled/skipped or inapplicable with a reason. The root independently inspects evidence before completing the goal. These are agent workflow instructions, not an unattended test runner; actual browser/dependency installation must be demonstrated on a frontend task rather than inferred from this document.
