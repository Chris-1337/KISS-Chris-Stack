# Goal: transparent renewal of expired managed SonarQube tokens

- Target: user-requested automatic renewal without another confirmation when an active agent needs an expired managed scanner or reader token; keep failures visible and gates enforced.
- Change: the bundled SonarQube skill now runs a renewal preflight before uploads, reads and goal checks, and the canonical policy routes normal goals through it. Stored token identity/owner/type/project/expiry metadata and protected owner credentials establish the renewal boundary. Healthy tokens and revoked/unknown credentials are not rotated.
- Safety: serialize refresh and re-read state, retain token scope/least privilege and finite expiry, validate actual intended operations, atomically preserve `.env` ACL/comments/unrelated entries, reload the child environment and retry once within the operation timeout. Revoke the old managed token only after successful persisted replacement; clean up only an unreferenced newly created orphan on failure. No password reset, permission expansion or shared/external authorization bypass.
- Checks: a separate test agent first demonstrated RED because the renewal instructions were absent. Both new renewal contracts pass; the full repository suite passed 109 tests, and the skill validator passed. Final focused checks passed after clarifying single-operation ordering and initial management metadata persistence. Live API inspection confirmed owner-scoped token search, nested project binding metadata and generation/revocation parameters; all three existing tokens were healthy and remained unchanged. Final gate evidence is recorded after independent evaluation.
- Current installation: enrolled all three healthy token identities under the canonical `.sonar-evidence/token-refresh.lock`. Fifteen nonsecret slot-specific management keys were appended after owner authentication, unique server-name/type/project/expiry validation and original-value checks. A protected empty staging file received the existing owner/ACL before secret bytes were written, then an unchanged-file check preceded atomic replacement. Original token/password values, unrelated bytes and comments were preserved; no token was generated or revoked.
- Final verification: the root reran all 109 tests successfully, with genuine Python line/branch coverage 96% and JavaScript coverage 100%. Actual scanner exit 0, task `c835ed8b-8817-4f86-914d-c061b93a3806`, analysis `a9430ac6-73f5-4201-b7b7-279deddb6f11`: gate `OK`, all ten conditions passed, no ignored conditions, overall coverage 96.5%, new-code coverage 96.6%, zero bugs/vulnerabilities/code smells/accepted issues and 100% reviewed hotspots. `.sonar-evidence/renewal-source-fingerprint.json` confirms all nine analyzed source/test/configuration files still match the uploaded snapshot; `.sonar-evidence/renewal-evidence.json` retains the summary separately from earlier verification.
- Healthy-token preflight: the root independently verified all three managed token slots under the canonical owner-only lock, with no rotation. Healthy credentials were not forced to expire; an actual expired-token replacement/revocation cycle remains untested. The instruction contracts and healthy-state enrollment do not establish that live failure-path behavior.
- Limits: this is an agent workflow, with no new authentication manager, executable helper or permanent daemon. Low-level scanner/read commands require the skill preflight; renewal cannot run while no agent/process is active. A live forced-expiry/replacement cycle is not claimed from instruction checks or read-only metadata inspection.
