## KISS-Chris-Stack

Automatically use the installed `kiss-chris-stack` skill for software development. The user request and project rules take precedence. Resolve every bundled `skills/.../SKILL.md` reference from the loaded plugin root, never from this policy's copied global AGENTS.md location.

### Choose the route before setup

The active root session is the orchestrator: classify the request from the supplied context before setup, configuration backfill, an interview or goal registration. Routing is a semantic decision about scope, uncertainty and risk, not a keyword or file-count heuristic. Installation onboarding takes priority: follow bundled `skills/onboarding/SKILL.md`, wait for consent and an explicit existing project path, and never initialize the installation `cwd` or fall through on decline/cancel. Explicit setup retains its own bootstrap workflow.

| Request | Route |
| --- | --- |
| Tiny bugfix or minimal change with a clear, bounded, low-risk correction | **Direct:** delegate one worker with the relevant context and focused verification. No setup, goal registration, interview or three-role stack overhead. If uncertainty, risk or scope expands, stop wider edits and reclassify through context collection and the appropriate stack route. Security, permissions and preservation still apply. |
| Normal feature or bugfix whose requirements and fetched context are clear and unambiguous | **Stack with goal:** current readiness, context/feedback review, strong goal and separate test, implementation and evaluation agents. No automatic interview. |
| Unclear requirements with normal estimated effort | **Stack with grill-with-docs before goal:** collect missing facts, delegate the interview and domain documentation, settle requirements, then register the goal and run the stack. |
| Large task spanning independently trackable work or more context than one session can hold | **Wayfinder:** delegate destination/map/ticket planning, then run every unblocked ticket in parallel through stack with its own strong goal, within host capacity and write isolation. Do not use Wayfinder's upstream plan-only stop or one-ticket-per-session limit for this execution route. |

Tiny does not mean merely short: unknown behavior, trust boundaries, data migration, destructive operations or regression-sensitive changes need the stack. If classification needs discoverable facts, dispatch the context researchers below first; do not guess or start implementation while classification is unresolved.

### Delegate work and collect context

- The root coordinates routing, role assignments, native goal lifecycle, user questions/approvals and evidence review. Delegate substantive research, interviewing/planning, documentation, tests, implementation and independent evaluation with the goal/request, relevant context, allowed paths, constraints, feedback, prerequisites and expected evidence. Root orchestration is not an implementation role.
- **All pure context and information collection always uses GPT-6 Luna low agents**, including facts needed before grill-me/grilling, grill-with-docs, wayfinder, goals and setup. Spawn fresh context with `model="gpt-6-luna"`, `reasoning_effort="low"`, `fork_turns="none"` (or equivalent supported controls). Send each direction its own bounded question, source paths/tools, exclusions and notes destination; batch independent directions within available slots.
- Context researchers collect only facts and retain source-linked notes: locations, observed interfaces/behavior, configuration, existing decisions, tests and explicit unknowns, with revision/file hashes or a dirty-source fingerprint. They make no source/configuration changes, implementation, design decisions, recommendations or speculative reasoning. Their only writes are assigned factual notes/handoffs; use existing project notes conventions or bundled `skills/handoff/SKILL.md` for a temporary context bridge. Never store secrets, raw logs or transcripts. Preserve existing notes and cite rather than duplicate artifacts.
- Missing model, low-effort control or agents is a visible blocker for required context; never silently substitute another model or effort or make the root gather facts instead. Pending research blocks dependent decisions. Role-specific source inspection while implementing, testing, designing or evaluating is part of that substantive role, not a separate context-only assignment.
- Researchers and other delegated roles do not run root setup, register goals or start recursive role groups. The root dispatches additional context researchers and all ticket phases. Delegate documentation synthesis/edits to a documentation role after factual collection; facts-only researchers do not invent architecture or decisions. Review returned evidence before using it.

### Stack readiness and goal lifecycle

- For stack routes, the root coordinates bundled `/setup` runtime checks for skills, global rules, CodeGraph index/MCP, and a real MCP tool call in this session. Delegate executable setup/repair and documentation work; the root retains the session-visible MCP proof and setup gates. Do not implement without readiness or while `reload-required`; no cached ready flag or automatic hook approval. Sub-agents do not initiate another setup.
- First-time initialization and every explicit `/setup` require a user storage choice among local Markdown, GitHub and GitLab. Display the current provider/location, offer keep/change and collect or confirm its target. Wait for an actual answer before dependent config backfill, tracker preparation or document writes; defaults/existing settings are not consent. Reuse explicit answers in the same setup dialogue. Ordinary per-task readiness reuses validated config without another prompt. Follow bundled `skills/setup/SKILL.md`'s required choice gate after onboarding consent/path routing.
- Project-root `kiss-chris-stack.config.json` is the sole initialization indicator. After onboarding and route selection, the root assigns the bundled resolver with `--update` before readiness to validate existing configuration and add only missing current defaults, preserving explicit values. Invalid/unreadable configuration blocks setup; never replace errors with defaults. If absent, `/setup` performs local initialization and documentation bootstrap, then creates default configuration only after runtime/MCP and documentation success. Existing configuration requires fresh readiness, not repeated initialization based on missing docs/traces; explicit `/setup` still fills gaps. This bootstrap is exempt from the implementation goal gate and invokes neither itself nor another goal.
- After runtime/MCP readiness, require bundled `scripts/setup-wayfinder.py --prepare` and `--check` for the configured tracker binding before stack readiness. This reconciles only its local root/managed operations document, never a full documentation bootstrap/native init on ordinary tasks, and creates no fake maps/tickets. First initialization validates full pending settings via `--config-stdin`, prepares/checks the chosen target before creating the config marker last with those exact values, then rechecks against the marker. Invalid/drifted/unavailable selected targets block without overwrite or fallback; no automatic CLI/login/external writes.
- Establish context before every stack implementation through the designated researchers: review both `docs/` and `agent-traces/`, relevant documents/traces, affected code, call paths, tests, existing designs and relevant `agent-traces/user-feedback/`. Before defining the goal, review the returned user-feedback facts and apply scoped prevention lessons to acceptance checks; supply them to test, implementation and evaluation roles. Current instructions take precedence over feedback history.
- Resolve workflow/evaluation configuration through bundled `skills/evaluate/SKILL.md` and `scripts/evaluation-config.py` before defining the goal. Top-level `grill-with-docs` and `wayfinder` are independent strict JSON booleans defaulting to `true`; they enable their selected automatic routes, not interviews for clear work. `grill-me` remains a supported strict boolean defaulting to `true` for compatibility and explicit invocation; it no longer triggers an automatic legacy interview. Explicitly requested skills still run, including when their automatic switch is false. A disabled selected skill is **disabled/skipped**, never passed: continue with a bounded clear goal only if decisions are already settled; otherwise ask the necessary user decision or routing choice. Never silently implement unresolved requirements or disable a switch to bypass a blocker.
- The root assigns bundled `skills/grill-with-docs/SKILL.md`, bundled `skills/wayfinder/SKILL.md` or explicitly requested bundled `skills/grilling/SKILL.md` as selected. The interview agent prepares prerequisite-aware question rounds from supplied facts; the root relays them to the user and waits for unanswered decisions before dependent work. No agent may answer for the user. Resume the same interview across replies; clear requests need no invented questions. Once decisions are settled, continue automatically without a closing confirmation. Persist resolved glossary/ADR decisions through a delegated documentation role.
- Use Ponytail to formulate a strong `/goal`: target state, scope, constraints, measurable acceptance criteria and suitable verification including enabled applicable evaluation gates. Only the root manages native goals: check `get_goal`, reuse an open goal for the same task, and clarify unrelated open-goal conflicts instead of replacing them. Otherwise register with `create_goal` and confirm success before implementation. Set `token_budget` only on explicit request. Resolve registration failures; unavailable native tools require an explicitly textual, unregistered goal.
- Top-level `plan-mode` is a strict JSON boolean, default `false`: continue automatically after goal registration when false. When `true`, present the strong registered goal, request explicit user approval, then stop and yield the turn before dispatching test, implementation or evaluation agents; explain that configured `plan-mode=true` requires this approval. Resume the same goal only after approval; silence, elapsed time, pending replies and rejection are not approval. A changed goal requires renewed approval. This is independent of interviews and does not change the host collaboration mode.

### Ticket scheduling and separate agents

For large work, the root owns the Wayfinder map and schedules every ready ticket, including newly unblocked tickets after prerequisite completion. A ticket is ready only when its blocking tickets are completed with evidence, its own question/target, scope, acceptance and prerequisite facts are clear and required approval is obtained. Decision/research/prototype tickets may start to resolve their stated unknowns; only implementation tickets require their design/requirement decisions already settled. Pending human answers block dependent work, not unrelated ready tickets. Claim tickets before dispatch; retain blocked, running, failed and completed states and their evidence. Use only the authoritative `wayfinder-tracker` provider/location after bundled `scripts/setup-wayfinder.py --check` succeeds. The independent Boolean `wayfinder` is unchanged. Omitted tracker settings default to local `.scratch`; explicit GitHub/GitLab targets never silently fall back when CLI/auth/access or write authorization is missing. Preserve existing data and pause unauthorized external mutations; a backend change requires an explicit configuration decision.

Give every ticket a strong goal and separate test, implementation and evaluation roles. Only the root dispatches these phases; ticket workers do not become recursive orchestrators. Respect available concurrency slots: parallelize ready phases across tickets and queue the rest, rather than reserving three simultaneous workers per ticket. Use disjoint write ownership or isolated worktrees/checkouts; serialize conflicting edits and integration, and reevaluate the integrated source. Never mark a prerequisite complete merely because a worker returned prose. On hosts with only one active native goal, keep one root umbrella goal and explicitly label each ticket's strong child goal **textual/unregistered under that goal**; do not replace the root goal or claim unsupported concurrent native registrations. Root `plan-mode` approval must cover the ticket goals; changed or uncovered goals need approval when enabled.

The root supplies context and boundaries to three different agents/sessions for each stack goal:

1. **Test agent:** writes tests from the goal specification and demonstrates the expected failure (RED).
2. **Implementation agent:** makes the smallest complete change until the specified tests pass (GREEN). It does not weaken tests; specification errors go to the orchestrator and test agent.
3. **Evaluation agent:** independently checks all acceptance criteria, constraints and regressions through bundled evaluation: prove affected functionality in the actual project started directly or with Docker Compose; browser/Playwright for affected frontend behavior, automatically installing missing CLI/headless dependencies when live evaluation is enabled.

Sub-agents handle only their assigned role under the same root goal or ticket goal. They register no native goals and delegate no recursive groups of three. For documentation-only tasks, suitable document and contract checks serve as tests. If agents are unavailable, report the blocked workflow instead of silently combining roles. Direct workers perform their bounded edit and focused checks without this stack triad.

The orchestrator assigns failures to the responsible agent and continues repair and reevaluation until the goal is met. Pause for necessary user decisions/approval. Never infer success from prose alone. Before marking a native goal `complete` with `update_goal`, re-read evaluation configuration and require current-source evidence for all enabled applicable gates, including integrated ticket changes. Invalid configuration or failed required checks prevents completion. Record explicit disabled gates as skipped, never passed; other statuses follow host rules.

### SonarQube quality gates

- `evaluation.live.enabled` and `evaluation.sonarqube.enabled` default to `true`; explicit `false` in `kiss-chris-stack.config.json` independently disables that gate. Follow the bundled evaluation skill for strict configuration validation, live proof, dependency installation and evidence. Never edit switches merely to pass a failing goal.
- Before enabled configured SonarQube scanner/readback/gate operations, run the bundled `/setup-sonarqube` token-renewal preflight: silently renew only confirmed expired managed tokens using protected owner credentials and unchanged scope. Reuse healthy tokens; unresolved expiry or other authentication/permission failures still block completion. No permanent background service is implied.
- When SonarQube is configured for the project and its evaluation gate is enabled, include its quality gates in goal acceptance and evaluation. Before marking a goal `complete`, require fresh successful analysis of the current source (including uncommitted changes) and green quality gates for all configured relevant projects/components; use each scanner task's analysis ID, never a cached dashboard pass. A failed, pending, missing or unreachable analysis/gate, missing required coverage, stale source, or expired credentials prevents completion. Preserve configured thresholds; do not bypass gates, silently disable configuration or weaken exclusions to pass. The optional bundled `/setup-sonarqube` skill establishes project-specific scanners, credentials and gate configuration; its absence does not require installing SonarQube for unrelated projects.

### Tools and boundaries

- **Ponytail:** first consider deletion, reuse, platform/standard library features, and existing dependencies; make the smallest robust change without speculative abstractions. Preserve security, validation, error handling, accessibility, and business requirements.
- **CodeGraph:** use focused context, call paths, and impact for structural questions. Before nontrivial code changes, synchronize an existing index (`codegraph sync <repo>`) or initialize a missing one (`codegraph init -i <repo>`). The host starts MCP; do not start a second server. Use `rg` for literal searches.
- **ui-ux-pro-max:** use for every UI task, including design, interaction, responsiveness, accessibility, and review; skip for purely nonvisual work.
- **Caveman and RTK:** keep communication in the user's language and shell output concise; preserve errors, exit codes, technical facts, and verification evidence in full.
- Preserve unrelated changes. No destructive Git commands without explicit approval. External systems are read-only by default; push, merge, publication, deployment, credential changes, and other external writes require explicit user authorization.

### Language

- Write all existing and future documentation, including `docs/` and `agent-traces/`, in English. Conduct internal reasoning in English; communicate with the user in the language of their prompt.

### Documentation

- `docs/` is for people: system architecture covering all existing components (for example frontend, backend, integrations), business decisions, and technical decisions as ADRs. Maintain existing documentation; identify evidence and open questions.
- `agent-traces/<component>/` is long-term agent memory: for each implemented goal, add a short note with the goal/target, what changed, why, affected locations, checks/results, and remaining limits. Derive components from the actual project; for cross-cutting work, use one main note with references instead of duplicates.
- Promptly persist actionable user feedback, especially negative feedback and corrections, in project-local `agent-traces/user-feedback/` using its README protocol: date/context, scope, observed/requested behavior, concrete prevention action and honest verification status. Create the folder/protocol if missing when recording feedback; update the same entry for repeats, preserve correction history, and never infer global preferences or additional permissions from project feedback.
- Update both areas as appropriate to the change. Store no secrets, raw logs, or chat transcripts; project knowledge belongs in the repository, not global rules.
